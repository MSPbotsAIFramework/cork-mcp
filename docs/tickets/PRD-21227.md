## Product design

### Goals / Non-goals

**Goals**: give the agent platform read-only access, per MSP client, to:
1. the client's Cork warranty/coverage status,
2. the client's Cork Cyber Score history, and
3. the client's compliance/risk events and software-vulnerability data,

so an agent (or a human asking an agent) can answer "is this client covered, and how exposed are they right now" without opening the Cork portal.

**Non-goals** (explicitly out of scope for this first version, see Tech design §9 "Decisions made by DEV01" for why):
- Anything that writes to Cork (connecting/updating/deleting an integration, provisioning a partner account, triggering a software install) — the ticket asks to "review," not to manage.
- Returning a Cork integration's raw stored credentials, or its bulk raw-sync-data export — both are credential/bulk-exfiltration-shaped and excluded regardless of whether the ticket asked for them.
- Invoices, distributor-partner administration, and software-installer tooling — Cork exposes these, but the ticket names none of them.
- Any UI change. This is a backend MCP connector; there is no MSPbots front-end surface in this ticket.

### Acceptance criteria AC1..AC8

- **AC1**: Given a valid Cork API key and a client identifier, when the agent asks for that client's warranty/coverage status, then the tool returns the client's current warranty/coverage state together with its most recent Cork Cyber Score, sourced from Cork's per-client record.
- **AC2**: Given a valid Cork API key and a client identifier, when the agent asks for that client's Cork Cyber Score history, then the tool returns the full score history for that client, newest first.
- **AC3**: Given a valid Cork API key and a client identifier, when the agent asks for that client's compliance/risk data, then the tool returns the client's compliance/risk events, each with its event type, whether it is currently at-risk, and whether it has been resolved.
- **AC4**: Given a valid Cork API key and a client identifier, when the agent asks for that client's vulnerability exposure, then the tool returns the client's software vulnerabilities (CVE id, CVSS score, EPSS score, known-exploited flag) and/or a per-vendor rollup summary.
- **AC5**: Given the Cork API key is missing or Cork rejects it, when any tool is called, then the tool returns a structured `unauthorized` error — never an unhandled exception, and never a silent empty result that could be misread as "no coverage."
- **AC6**: Given any tool that reads data for one client, when it is called without a client identifier, then the tool returns a structured `invalid_argument` error and never calls Cork's API in a way that would return every client under the account — the single Cork API key covers the whole MSP account, so an unscoped call is a cross-client data leak, not a convenience.
- **AC7**: Given a client that currently has no warranty record, no compliance events, or no vulnerabilities, when the corresponding tool is called, then it returns an empty list — not an error, and not indistinguishable from an auth failure.
- **AC8**: Given more matching records exist than fit in one page, when a list-returning tool is called, then the response is bounded (a capped page size) and signals that more data exists, rather than returning an unbounded payload or silently dropping the remainder.

## Tech design

### Conclusion

Build `MSPbotsAIFramework/cork-mcp` as a new Python/FastMCP vendor-MCP server (per `vendor-mcp-development` SOP §9's recommended stack) with 6 read-only tools against Cork's REST API (`https://api.corkinc.com/api/v1`, static Bearer key). Every client-scoped tool requires a `client_uuid` argument — Cork's one API key covers an MSP's entire client roster, so making the client identifier optional would let one call return another client's warranty, score, or risk data. No public Cork developer-portal docs exist; the API surface below is taken from a read-only review of the open-source `WYRE-AI/cork-mcp` reference implementation (same party as the ticket's own `conduit.wyre.ai` link) and cross-checked against Cork's own customer-facing integration help pages (`help.corkinc.com`), not copied or forked into this repo.

### Where the current implementation lives

Nothing exists yet. `MSPbotsAIFramework/cork-mcp@main` (6ee3c0d) is the two-line README scaffold described in Current state — there is no prior Python/Node code, no prior tool, nothing to extend.

### Data & API contract

All 6 tools call Cork's REST API read-only; none accept Cork-side write parameters.

**Credential**: header `X-Cork-Api-Key` (gateway-injected per request, SOP §3.1 naming convention `X-<Vendor>-<Credential>`), forwarded to Cork as `Authorization: Bearer <key>`. `credential_fields` for gateway registration:

```json
{
  "X-Cork-Api-Key": {
    "label": "Cork API Key",
    "type": "password",
    "required": true,
    "description": "Bearer API key generated in Cork's Admin UI (Settings -> API). Scoped to the whole MSP account, not to individual clients.",
    "example": "ck_live_********"
  }
}
```

**`cork_get_clients(page=None, page_size=None)`** → `GET /clients`. Response: list of clients, each with `uuid`, `name`, `warranty_status`, `latest_cyber_score`, plus pagination metadata. Covers AC1's "coverage status" half directly.

**`cork_get_warranties(client_uuid, page=None, page_size=None)`** → `GET /warranties?client_uuid=...`. Response: list of active cyber-warranty packages for that client (package name, coverage limits, effective/expiry dates). Covers AC1's "warranty" half.

**`cork_get_client_score_history(client_uuid, created_after=None, created_before=None, page=None, page_size=None)`** → `GET /clients/{client_uuid}/score-history`. Response: list of `{score, created_at}` entries, newest first (matches AC2).

**`cork_get_compliance_events(client_uuid, show_resolved=None, at_risk=None, page=None, page_size=None)`** → `GET /compliance/client/{client_uuid}/events`. Response: list of events with `event_type`, `at_risk`, `resolved`, `created_at` (AC3).

**`cork_get_compliance_event_types()`** → `GET /compliance/event-types`. Response: static reference list (event type code, description, cure period) used to interpret the `event_type` field above — not client-scoped, no `client_uuid` needed, no per-tenant data.

**`cork_get_software_vulnerabilities(client_uuid=None, minimum_cvss_score=None, only_known_exploited=None, page=None, page_size=None)`** → `GET /vulnerabilities/software?client_uuid=...`. Response: list of CVEs with `cvss_score`, `epss_score`, `known_exploited`, affected software (AC4). **Exception to the "client_uuid required" rule**: Cork's own endpoint allows an account-wide query; this tool keeps `client_uuid` optional but every MSPbots-facing call path (agent-invoked) must pass it — documented as a must-fix item for code review (§ Non-functional, multi-tenant).

**Errors** (SOP §4.2 envelope, same shape from every tool):

```json
{"error": {"code": "unauthorized", "message": "Cork rejected the API key", "retryable": false}}
```

Codes used: `not_configured` (no `X-Cork-Api-Key` header at all), `unauthorized` (Cork 401), `invalid_argument` (missing required `client_uuid`, or `page_size` out of range), `rate_limited` (Cork 429, `retryable: true`), `upstream_error` (any other non-2xx).

**Backward compatibility**: not applicable — first version of a new connector, no existing callers.

### Key flow / sequence

```
Agent -> Gateway: tools/call cork_get_clients {page_size: 20}
Gateway -> cork-mcp: POST /mcp  (header X-Cork-Api-Key: <key>)
cork-mcp: read credential from request context (never from env in gateway mode)
cork-mcp -> Cork API: GET /clients?page_size=20  (Authorization: Bearer <key>)
Cork API -> cork-mcp: 200 {data: [...], has_more: true, ...}
cork-mcp -> Gateway -> Agent: tool result (JSON string, compact, ensure_ascii=False)
```

Error path (missing client_uuid on a client-scoped tool): cork-mcp returns `{"error": {"code": "invalid_argument", ...}}` **without calling Cork's API at all** — the validation happens before the outbound request, so an unscoped call can never reach Cork and can never return cross-client data (AC6).

### Non-functional

- **Idempotency & concurrency**: all 6 tools are read-only GETs; no idempotency concern. Credentials are read from a request-scoped context var (SOP §3.3), never a module-level global, so concurrent requests for different MSP accounts cannot see each other's API key.
- **Performance**: Cork's list endpoints are paginated server-side; this connector passes `page`/`page_size` through and caps `page_size` at 200 (SOP §2.5 ceiling), defaulting to 50. No local caching in v1 — Cork's own data (warranty status, score, compliance events) changes slowly enough that caching isn't needed to meet the ticket's "review" use case, and caching would add a staleness risk for a security-relevant signal.
- **Security**: the Cork API key is never logged, never persisted, never defaulted from an env var in gateway mode (SOP §3.1-3.3). `cork_get_software_vulnerabilities`'s `client_uuid` is optional at the Cork-API level but must be enforced as effectively-required at the MSPbots tool-description/validation level — documented above as a review item, not deferred silently.
- **Multi-tenant isolation**: this is the central risk this design exists to manage. Cork's integration model issues one API key per MSP account covering every client that MSP manages; MSPbots itself is multi-tenant on top of that. AC6 and the "no `client_uuid` → `invalid_argument`, never call Cork" rule (Key flow above) are the enforcement point: every client-scoped tool must reject an unscoped call before making the outbound request, so a prompt or agent bug can never fan out into "list every one of this MSP's clients' warranty data" by omission.
- **Observability**: structured logs on every Cork call: `client_uuid` (not the API key), tool name, Cork response status, latency. No response bodies in logs (compliance/vulnerability data is sensitive).

### Rollout & rollback

No feature flag — this is a new, standalone MCP server with no existing traffic. Rollout is: merge to `main` → `mcppub register` (new vendor, not yet known to the INT deploy API) → INT health check. Rollback is reverting the merge commit on `main` and re-publishing; since nothing else depends on this connector yet, there is no multi-repo rollout ordering (`release order: n/a — single new repo, no dependents`).

### Test strategy

Unit tests (mocked Cork API via `respx`) for: each tool's URL/params construction, the 401→`unauthorized` / 429→`rate_limited` / other-non-2xx→`upstream_error` mapping, the missing-`client_uuid`→`invalid_argument` short-circuit (asserting the mock was never called), empty-list passthrough, and page-size clamping. No integration test against the real Cork API in CI — the dev leg has no Cork test account; tests needing one are marked `manual · needs a real vendor account` per `.ac.json` and do not block `6b`. Regression surface: none — new repo, no existing tools to break.

### Effort & breakdown

Rough order of magnitude: 1.5–2.5 developer-days for the dev leg (scaffold + config + 6 tools + mocked tests + README + Dockerfile is the bulk of it; the range's uncertainty is mostly "how much the mocked Cork response fixtures need to deviate from the WYRE-AI reference's assumptions once real field names are probed against a sandbox key, if one becomes available"). Suggested single sub-task — the whole connector is small enough that splitting it would just add coordination overhead for one developer.

### Risks & dependencies

- **Risk**: field names/response shapes are inferred from a third-party open-source reference, not Cork's own docs. Mitigation: tests assert against the shapes documented in that reference; if a real Cork key becomes available before release, re-verify field names against a live call before `6c`.
- **Risk**: Cork may rate-limit aggressively (429 is a first-class error class in the reference, suggesting this is a known concern). Mitigation: `rate_limited` is `retryable: true` in the error envelope so callers can back off; no retry-with-backoff built into the connector itself for v1 (SOP baseline, not a gap specific to this ticket).
- **Dependency**: none on other open tickets or repos. Single new repo, no gateway change, no platform-side change.
